# Face-X

Youth football registration and event-day face check-in.

| Path | What |
| --- | --- |
| `apps/web` | Frontend (`@facex/web`): Next.js 14 (App Router), TypeScript, Tailwind. |
| `apps/api` | Backend (`@facex/api`): Node 22, Express 5, TypeScript, Zod, PostgreSQL (`pg`), JWT auth, S3-compatible private storage. |
| `apps/api/db` | SQL migrations and development seed. |
| `docs/` | `architecture.md` (decisions), `database.md` (schema, guarantees), plus the document-verification contract. |

The backend is built in phases. **Done:** foundation, PostgreSQL schema, authentication and authorization (Supabase was removed; it is
plain PostgreSQL + our own auth). Registration, documents, consent, payments (Stripe), readiness, face enrollment and the event-day backend foundation are implemented; no real face provider adapter and no frontend integration yet.
Design decisions and open questions: `docs/architecture.md`.

## Prerequisites

- Node 22+
- pnpm 9 (`corepack enable` then `corepack prepare pnpm@9 --activate`; or `npm i -g pnpm@9`). The repo is a pnpm workspace; npm is not used.
- A PostgreSQL database (local install, Docker, or managed). Tests do not need one: they start a real embedded PostgreSQL.

## Monorepo commands (run from the repository root)

```bash
pnpm install        # installs every app (one lockfile)
cp apps/web/.env.example apps/web/.env.local   # frontend settings (NEXT_PUBLIC_*, API_ORIGIN)
cp apps/api/.env.example apps/api/.env         # backend settings (database, secrets)
pnpm dev            # web (http://localhost:3000) + api (http://localhost:4000) together
pnpm dev:web | pnpm dev:api
pnpm build          # api, then web;  or pnpm build:web | pnpm build:api
pnpm start:web | pnpm start:api   # run the production builds
pnpm lint | pnpm typecheck | pnpm check   # check = lint + typecheck, all apps
pnpm test           # API tests (start their own embedded PostgreSQL)
pnpm db:migrate | pnpm db:seed
```

Env files are per app and never shared: `apps/web` only sees `NEXT_PUBLIC_*` / `API_ORIGIN`; secrets live only in `apps/api/.env`.
Shared code goes in `packages/*` (already in the workspace globs) once something is genuinely shared; nothing is yet.
The link-preview card is a static image (`apps/web/src/app/opengraph-image.png`), so `next build` works on Windows and Linux alike. It is generated by `pnpm --filter @facex/web generate:og` (see the comment in `apps/web/scripts/generate-og.mjs` for why it is not a Next route: Next 14's bundled renderer breaks on Windows paths). Re-run that script if you change the design.

### Player flow against the real API

The player registration flow (`/login`, `/signup`, `/register/player`, `/register/player/payment-return`, `/dashboard/player`) talks to the API
through this app's own `/api/v1`, which `next.config.mjs` proxies to `API_ORIGIN` (default `http://localhost:4000`). Start the API first, and
make sure its `FRONTEND_URL` includes this app's origin (e.g. `http://localhost:3000`). File upload needs the API's `STORAGE_*` variables
(and CORS on the bucket for this origin); payment needs `STRIPE_*`, with the Stripe return URL pointing at
`/register/player/payment-return`. Coach and staff registration (`/register/coach`, `/register/staff`) use the same API: sign in, then details -> photo and certificates (real uploads) -> submit. The Admin site is covered under "Admin site" below.

## Local setup and deployment

- **Local database:** `apps/api/db/setup/create-database.sql` creates a database with a migrator user (owns the tables) and a restricted app user,
  and is safe to re-run. Use one database for real data and a second for demo/test data (`-v db_name=facex_dev`, then `db:migrate` and `db:seed`).
- **Local file uploads without any cloud account:** set `STORAGE_DRIVER=local` in `apps/api/.env`. Files go to `apps/api/.local-storage/`
  (git-ignored) through the same signed-link flow a bucket uses. It is refused when `NODE_ENV=production`.
- **Moving to a server (Hetzner or any Linux host):** everything environment-specific is an environment variable. See
  [docs/deployment.md](docs/deployment.md) for the topology, the full settings reference, the steps and a rough effort estimate.

## Run the API

`apps/api` is a workspace package; `pnpm install` at the root covers it. Commands can be run from `apps/api` or, with `pnpm dev:api` etc., from the root.

```bash
cd apps/api
cp .env.example .env              # then fill in DATABASE_URL, JWT_SECRET, REFRESH_TOKEN_SECRET
pnpm db:migrate                   # create the schema
pnpm db:seed                      # optional, development data only
pnpm dev                          # http://localhost:4000
curl localhost:4000/health        # liveness
curl localhost:4000/health/ready  # readiness: also checks the database
```

Generate each secret with `node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"` (two different values).
Scripts: `dev`, `build`, `start` (runs `dist/`), `typecheck`, `lint`, `format`, `format:check`, `test`, `db:migrate`, `db:seed`.
From the repo root: `pnpm dev:api`, `pnpm build:api`, `pnpm test`, `pnpm lint`.

### Authentication

```text
POST /api/v1/auth/register   {email, password, fullName?}  -> 201 user (no roles)
POST /api/v1/auth/login      {email, password}             -> 200 {accessToken, expiresIn, user} + HttpOnly refresh cookie
POST /api/v1/auth/refresh    (cookie)                      -> 200 new accessToken + rotated refresh cookie
POST /api/v1/auth/logout     (cookie)                      -> 204, session revoked
GET  /api/v1/auth/me         Authorization: Bearer <accessToken>
```

Access tokens last 15 minutes; refresh tokens rotate on every use and live only in an HttpOnly cookie. New accounts have **no roles**.
A signed-in account picks PARENT, PLAYER, COACH or STAFF itself (below; COACH and STAFF grant no event access until a registration is approved); ADMIN is granted in SQL, e.g.
`insert into public.user_roles (user_id, role) values ('<user id>', 'ADMIN');`. Details: `docs/architecture.md`.

```text
POST /api/v1/users/me/roles   {role: 'PARENT' | 'PLAYER' | 'COACH' | 'STAFF'}  -> {roles}   idempotent; ADMIN or anything else -> 422

Coach / staff registration (same registrations, documents, consents and readiness endpoints as players):
POST|GET /api/v1/staff-profiles, GET|PATCH /api/v1/staff-profiles/:id          the person (one COACH and/or one STAFF profile per account)
POST /api/v1/registrations {eventId, staffProfileId, teamId?}                    GET /registrations?registrantType=COACH|STAFF
no payment step: SUBMITTED -> DOCUMENT_REVIEW -> VERIFIED (admin approves documents) -> READY_FOR_EVENT (coach: after AB 506)
```

### Events, teams and invites (reference data)

Any signed-in user can read these. Drafts are invisible (404); invite codes are never returned.

```text
GET  /api/v1/events                    PUBLISHED events, soonest first
GET  /api/v1/events/:eventId           a PUBLISHED or CLOSED event ({registrationOpen})
GET  /api/v1/events/:eventId/teams     ACTIVE teams of that event
GET  /api/v1/teams/:teamId             one team + its event
POST /api/v1/teams/resolve-invite      {inviteCode, teamId?} -> {team, event}; every failure is the same 404 INVITE_NOT_FOUND; rate limited per user
```

### Players and registrations (Phase 4A)

All need `Authorization: Bearer <accessToken>`. Creating and editing need the PARENT or PLAYER role (`POST /users/me/roles`).

```text
POST  /api/v1/players                       create a child (PARENT, with a guardian) or yourself ({forSelf:true}, PLAYER)
GET   /api/v1/players                       your players
GET   /api/v1/players/:playerId             owner, or an admin of an organization the player is registered with (read-only)
PATCH /api/v1/players/:playerId             owner; locked once a registration is submitted
POST  /api/v1/players/:playerId/parents     add another guardian record (no account)

POST  /api/v1/registrations                 {eventId, playerId, teamId?, guestCount?} -> DRAFT
GET   /api/v1/registrations                 your registrations; optional ?eventId=&playerId= filters
GET   /api/v1/registrations/:id             owner, or admin of the event's organization (read-only)
PATCH /api/v1/registrations/:id             edit the DRAFT (save as draft)
POST  /api/v1/registrations/:id/submit      DRAFT -> SUBMITTED
GET   /api/v1/registrations/:id/status      status + history
```

Registrations you cannot access return 404. Rules and open decisions: `docs/architecture.md` ("Players, guardians and registrations").

### Documents and consent (Phase 4B)

Document and consent endpoints need `Authorization: Bearer <accessToken>`. File operations need the `STORAGE_*` variables (otherwise 503).

```text
POST  /api/v1/registrations/:id/documents/upload-url   {documentType, fileName, mimeType, sizeBytes} -> signed PUT URL (PARENT/PLAYER)
POST  /api/v1/documents/:id/complete                   verify the stored file (size + file signature)
POST  /api/v1/documents/:id/submit                     send for review
PATCH /api/v1/documents/:id/review                     ADMIN: {decision: APPROVED} or {decision: REJECTED, reasonCode, reason}
GET   /api/v1/registrations/:id/documents              documents + completeness (separate from registration status)
GET   /api/v1/documents/:id                            metadata
GET   /api/v1/documents/:id/download-url               short-lived signed download URL

GET   /api/v1/registrations/:id/consents               requirements, current published wording, recorded acceptances
POST  /api/v1/registrations/:id/consents               {consentId, signedName, accepted: true}
```

Workflow, access rules and open decisions: `docs/architecture.md` ("Documents and consent").

### Admin review

For an ADMIN of the organization that owns the event (anyone else: 403 `EVENT_ACCESS_DENIED`). Player registrations only for now.

```text
GET  /api/v1/admin/events                           the organization's events, any status (the event picker)
GET  /api/v1/admin/events/:eventId/summary          registrations by status, documents awaiting review, payments (paid count/amount, refunds)
GET  /api/v1/admin/events/:eventId/registrations    ?status= &teamId= &search=(name or FX number) &documentsPending=true &page= &pageSize=(<=100)
GET  /api/v1/admin/events/:eventId/review-queue     submitted, undecided documents, oldest first (?page= &pageSize=)
POST /api/v1/admin/registrations/:id/reject         {reason} -> REJECTED (final); the reason is in the status history the family can read
PATCH /api/v1/admin/registrations/:id/event-access  {disabled, reason?} -> switch event-day access off/on (idempotent, audited)
```

Lists answer `{items, page, pageSize, total}`; drafts are hidden unless `status=DRAFT`. Document decisions already exist:
`PATCH /api/v1/documents/:id/review` (approve, or reject with a reason code and text: the family then replaces the file and it
returns to the queue), and `GET /api/v1/documents/:id/download-url` opens a file for an admin. When every required document is
approved and payment and consent are done, the registration reaches `READY_FOR_EVENT` by itself.
Event-day access is separate from the status: while it is off, check-in is refused whatever the status is; switching it on overrides nothing
(payment, documents and consent are still re-checked at the door). The reason (optional, disabling only) is an admin note, not shown to families.
Rejecting follows the status workflow (SUBMITTED, DOCUMENT_REVIEW or VERIFIED only), does not refund, and is not reversible.

### Admin site

Every admin screen (`/admin/...`) runs on the API. Staff sign in with a real account that has the ADMIN role and an organization (`user_roles` +
`users.organization_id`, granted in SQL for now); any other account is told it isn't an admin, and every endpoint below re-checks the role and that the
event belongs to the caller's organization (404/403 otherwise). There is no demo passcode any more.

| Screen | Endpoints (all under `/api/v1`) |
| --- | --- |
| Tournaments | `GET/POST /admin/events`, `GET/PATCH /admin/events/:eventId` (name, description, location, time zone, start/end, player fee, status DRAFT / PUBLISHED / CLOSED; an event with registrations cannot go back to draft) |
| Teams | `GET/POST /admin/events/:eventId/teams`, `GET/PATCH /admin/teams/:teamId` (name, club, division, ACTIVE / DISABLED; the invite code is shown to admins only; a duplicate name + club is 409) |
| Players / Coaches / Staff | `GET /admin/events/:eventId/registrations?registrantType=PLAYER\|COACH\|STAFF&status&teamId&search&documentsPending&page&pageSize`, `GET /admin/events/:eventId/summary?registrantType=`, then the registration, documents, consents and readiness endpoints above |
| Decisions | `PATCH /documents/:id/review`, `POST /admin/registrations/:id/reject`, `PATCH /admin/registrations/:id/event-access` (any kind of registration) |
| Coach team (`/register/coach`, `/coach/my-team/*`) | `GET/POST /registrations/:registrationId/team` (an approved coach creates their team once; the invite code is theirs to share), `GET /registrations/:registrationId/team/roster` (players and staff of their own team, open only while the coach is READY_FOR_EVENT and access is on; never documents, payments or emails) |
| Event Day | `GET /admin/events/:eventId/roster` (everyone with their standing, photo document and check-in), `POST /events/:eventId/check-ins` (manual, idempotent by `clientRequestId`), `GET /events/:eventId/search-players` |

Event Day keeps working with no connection: the roster is cached on the device and a check-in made offline is queued (IndexedDB) and sent when the
connection returns, each with its own request id so a retry never counts twice. The server stays the truth: it records one check-in per person
(whichever request it sees first wins, with its own clock) and answers a second device "already checked in", which the device then shows.
The device copy belongs to one admin and one event, is used only for them, is not used after 48 hours, and is removed when the admin signs out or
another admin signs in; a check-in still waiting is kept and is only ever sent by the admin who made it. A failed send is retried with growing
waits (2 s up to a minute), and a check-in the server refuses is kept with its reason for the admin to retry or dismiss.
The device reads the roster page by page (`GET /admin/events/:id/roster?page&pageSize`, up to 500 a page, no limit on the whole roster), and
each queued check-in carries an optional device id and the time the device recorded it (`deviceId`, `deviceCheckedInAt`) that the server keeps
in its audit record only; a second device that loses the race is told when (server time) and how the first check-in happened. Reloading the page
while fully offline is not supported (signing in needs the server). Face matching on the scanner needs a face provider, which does not
exist yet: until then use **Manual Search & Approve** (the scanner says so). The registration links an admin copies (`/tournament/:eventId/register`)
use the real event and team ids; a team-specific link carries the team's invite code and goes straight into the registration form.

### Payments (Phase 4C)

Stripe hosted Checkout. The browser redirect is never proof of payment: only a signed Stripe webhook marks a payment paid.

```text
POST /api/v1/registrations/:id/payment    start (or retry) a checkout for the server-side amount -> {paymentId, checkoutUrl, expiresAt}   (PARENT/PLAYER, body must be {})
GET  /api/v1/registrations/:id/payment    payment state (owner, or admin of the event's organization); poll this after the redirect back
POST /api/v1/webhooks/stripe              Stripe only: signature verified, each event applied exactly once
```

Needs `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` (without them these answer 503). For local testing use the Stripe CLI in test mode:
`stripe listen --forward-to localhost:4000/api/v1/webhooks/stripe` prints the `whsec_...` secret to use. Flow, states, idempotency and open
decisions: `docs/architecture.md` ("Payments").

### Registration readiness (Phase 4D-B0)

A registration moves `PAYMENT_COMPLETED -> DOCUMENT_REVIEW -> VERIFIED -> READY_FOR_EVENT` automatically, as the system, when payment (or a zero fee),
required documents and required consent are in place. No face profile is needed. It re-checks after a payment is confirmed and after a document
submission, document review or consent is recorded.

```text
GET  /api/v1/registrations/:id/readiness            status, ready, blockers, payment / documents / consent facts (owner, or admin of the organization)
POST /api/v1/registrations/:id/readiness/evaluate   idempotent re-check; empty body; never forces anything
```

Rules, locking design and open decisions: `docs/architecture.md` ("Registration readiness").

### Face enrollment (Phase 4D-A, foundation only)

Provider-independent; **no real face provider is integrated**, so these answer 503 until an adapter is registered and configured.

```text
POST   /api/v1/players/:id/face-profile   {documentId}  enroll from an approved registration photo (PARENT/PLAYER owner)
GET    /api/v1/players/:id/face-profile                 NOT_ENROLLED | ACTIVE | REVOKED (owner, or admin of the organization)
DELETE /api/v1/players/:id/face-profile                 remove at the provider and revoke (owner)
```

Only an opaque provider reference is stored in PostgreSQL: no image, template or embedding. Design, privacy decisions and open questions:
`docs/architecture.md` ("Face recognition foundation").

### Event-day check-in (Phase 4D-B2, backend foundation)

Operated by an **ADMIN of the event's organization** (COACH/STAFF scanner access is pending a product decision; PLAYER and PARENT never).
The frontend scanner is still a placeholder and is not connected.

```text
POST /api/v1/events/:eventId/face-scan     body = the raw image (Content-Type image/jpeg|png|webp, max 2 MiB), processed in memory only
                                           -> {scanId, result: MATCH | REVIEW_REQUIRED | NO_MATCH, ...}; 503 FACE_NOT_CONFIGURED without a provider
POST /api/v1/events/:eventId/check-ins     {method: "FACE", scanId, clientRequestId}  or  {method: "MANUAL", registrationId, clientRequestId}
                                           -> 201 (or 200 for an exact retry); 409 ALREADY_CHECKED_IN / SCAN_ALREADY_USED / PLAYER_NOT_ELIGIBLE ...
GET  /api/v1/events/:eventId/search-players?q=...   min 3 chars, max 20 results: name prefix, registration number, school ID, exact date of birth
```

Eligibility is re-checked against the current database state on every check-in (never just `READY_FOR_EVENT`); there is no override. No face provider
adapter exists yet, so scanning answers 503 until one is registered; manual check-in and search work now. Rules, flow, idempotency and open product
decisions: `docs/architecture.md` ("Event-day check-in").

### Environment variables (`apps/api/.env`)

| Variable | Required | Notes |
| --- | --- | --- |
| `DATABASE_URL` | yes | `postgres://user:pass@host:5432/db` |
| `DATABASE_SSL` | no | `true` for managed databases that require TLS |
| `JWT_SECRET` | yes | at least 32 characters; signs access tokens. Backend only |
| `REFRESH_TOKEN_SECRET` | yes | at least 32 characters, different from `JWT_SECRET`; keys the refresh-token hash. Backend only |
| `FRONTEND_URL` | yes | CORS origin(s) and cookie-endpoint Origin check, comma-separated |
| `ACCESS_TOKEN_TTL_SECONDS`, `REFRESH_TOKEN_TTL_DAYS` | no | defaults 900 and 30 |
| `COOKIE_SAME_SITE`, `COOKIE_SECURE` | no | default `lax`; secure by default in production |
| `STORAGE_ENDPOINT`, `STORAGE_REGION`, `STORAGE_ACCESS_KEY`, `STORAGE_SECRET_KEY`, `STORAGE_BUCKET`, `STORAGE_FORCE_PATH_STYLE` | not yet | private S3-compatible bucket; set access key, secret and bucket together; used from the documents phase |
| `NODE_ENV`, `PORT`, `LOG_LEVEL`, `DATABASE_POOL_MAX` | no | |
| `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` | for payments | backend only; without them payment endpoints answer 503 |
| `FACE_PROVIDER` (`node-native`), `FACE_ENCRYPTION_KEY`, `FACE_CONSENT_CODE` (`BIOMETRIC_CONSENT`), `FACE_PROVIDER_TIMEOUT_MS` | for face matching | `node-native` runs face-api inside the API (no cloud, no native build); `FACE_ENCRYPTION_KEY` is 32 random bytes, base64, used to encrypt stored face templates (required with `node-native`). Enrollment stays disabled until the consent policy is set (`NONE` waives it explicitly) |
| `FACE_PROVIDER_API_KEY`, `FACE_PROVIDER_URL` | no | reserved for hosted providers; unused by `node-native` |
| `FACE_MATCH_THRESHOLD`, `FACE_REVIEW_THRESHOLD`, `FACE_AMBIGUITY_MARGIN`, `FACE_SCAN_TIMEOUT_MS` | no | event-day matching policy; provisional defaults 0.90 / 0.75 / 0.05 / 5000. Calibrate against the chosen provider |

The API refuses to start, and lists the offending variable names (never their values), if a required one is invalid.

## Tests

```bash
cd apps/api && pnpm test
```

The suite runs against a **real PostgreSQL server**: `tests/global-setup.ts` starts one with `embedded-postgres` (real PostgreSQL
binaries, no Docker) and migrates it. To use your own server instead, set `TEST_DATABASE_URL` to a disposable server whose user can
create databases. Nothing is mocked except where a test says so (a deliberately failing database, a recording storage provider).
Storage uploads/downloads are checked up to URL signing only; they have not been run against a real bucket.
